# Support-led account erasure: local safety patch and operator runbook

**Unpublished proposal. No real account has been disabled or erased.** Based on main `45994aa77d3204024143536a8131124da793447d`, on local branch `codex/noeis-support-erasure-20261011`. This is a narrow access-safety patch plus tested preparation/checklist helpers. It is not a complete account-delete product, an online erasure command or a current public guarantee.

## What the patch changes

`accountAccessService.js` replaces the duplicate inline browser JWT middleware. After checking a JWT, the API now checks the current User record using the existing `_id` index. Missing accounts or `accountDisabledAt` markers deny access, including on optionally authenticated routes. Database failure returns 503 rather than granting access. Legacy users without the new field remain active; no backfill or shared-secret rotation is required.

The same current-account check gates agent/MCP tokens, personal-agent keys, bridge tokens, and OAuth code/refresh issuance. Disabled accounts cannot sign in. Pending Notion/Readwise import callbacks check account availability before provider exchange and again before storing a connection. Email-in ignores disabled users. An already running request or background job is not cancelled by these checks.

Independent review found and corrected two issues in the initial local patch: malformed cookie decoding outside the async middleware catches, and inconsistent errors for unavailable account lookups. Required browser authentication now returns a generic 401 for malformed credentials; optional authentication keeps its anonymous fallback. A valid Bearer header takes precedence over cookie decoding. Browser, agent, personal-agent and bridge account lookup failures return generic 503 responses, while OAuth issuance returns no-store 503 `temporarily_unavailable`; these new failures expose no database diagnostics. Verified inactive accounts retain the appropriate 401 or OAuth `invalid_grant` response.

`accountErasurePreparation.js` is an operator-only helper, not an HTTP route or live CLI. It requires explicit maintenance verification before any preparation writes, disables the exact account first, then revokes its local OAuth/agent access, cancels its approved device sessions, disables personal agents and removes locally held import credentials. It preserves the original disabled timestamp on reruns. A later failure leaves the account disabled; it must be retried and verified. It makes no network/provider call and deletes no workspace content. Local credential removal does not revoke a token at its external provider.

The helper also builds read-only record counts and a restart checklist. These are not process detectors or proof of complete production inventory. They cannot replace an operator's verification.

## Required maintenance procedure — do not execute without separate approval

1. **Verify the request and scope.** Use the owner-approved support contact and an established account-control verification method; do not trust a display name or email alone. Identify the exact internal ObjectId. Agree whether the request covers selected material or whole-account closure. Never ask for a password, API key or sign-in token. If an export is requested, arrange private authenticated delivery before erasure. Do not email workspace contents automatically.
2. **Establish a maintenance window.** Stop incoming mutating requests, webhooks and OAuth callbacks. Stop every API instance, worker, scheduler, external agent and maintenance script that can write to this database. Drain in-flight work or terminate its processes, then discard every process's transient queues by shutting it down. Pausing a browser is insufficient. Do not erase while another instance, job or external writer remains active. Identify and stop queued external retries as well. This affects service availability and requires explicit operational approval; this task has not stopped anything live.
3. **Capture the inventory before removing any parent record.** Load the current model registry plus OAuth models in an approved, isolated operator session. Call `readAccountRecordInventory` for the verified id. Preserve its exact scope queries and parent IDs using BSON Extended JSON, which preserves ObjectId types. Reconcile actual database collection names against the schema inventory and inspect legacy/orphaned records, nested Mixed payloads and files. A model-based count is not a scan of all physical storage. Resolve every unmapped namespace before proceeding.
4. **Prepare and revoke.** Only after independently verifying all writers are stopped, invoke `prepareAccountForErasure` with the verified model set/id and maintenance checklist. Verify the User is disabled and all scoped revocations completed. Stop on any failure; do not restore access to recover from a partial run. Request provider-side revocation where supported under separate authorization. Do not rotate shared secrets or disturb other users.
5. **Perform the separately reviewed cleanup while writers remain stopped.** This patch deliberately supplies no broad `deleteMany` command. The operator must review exact scoped queries and remove owned content, revisions, imports, credentials, jobs, caches, vectors and public snapshots under the approved deletion/retention policy. Capture Board child IDs before removing Boards; remove their dependent items/edges. Preserve other users' independently owned records and review cross-account references separately. Remove the User record last if full closure is the agreed policy. A disabled User row and its content are still retained data, not a completed erasure.
6. **Verify with the original scopes.** Call `recountAccountRecordInventory` using the captured inventory; do not reconstruct child queries from already removed parents. Reconstructing Board IDs after deleting Boards could hide orphaned items/edges. Check all account-owned active records and every queued job are gone. Separately inspect unregistered/legacy storage and provider/file records. Do not equate a null count with zero. Run `assertErasureResumeReady` only with verified active-record/job counts and no unresolved storage coverage. Its booleans are checklist acknowledgements, not automatic verification.
7. **Restart and verify denial.** Restart only after approved active-data cleanup, queue removal and retention exceptions are accounted for. Fresh processes discard in-memory queues; removed credentials and queued records prevent replay of the captured work. Test an existing browser session, existing connector access/refresh and pending import state through a secure channel: they must be denied. Recheck for recreated records and external webhook retries. Never put the credentials into a report. If denial or recreation checks fail, stop affected processing and investigate; do not report completion.
8. **Respond and retain a minimal receipt.** State what was removed from active storage and what remains under the documented log/backup/provider schedule. Keep only the approved minimum request/completion receipt for an approved duration. Do not promise a fixed turnaround, complete immediate erasure or legal compliance that has not been established.

If all writers cannot be stopped and verified, **do not use this procedure for erasure**. Safe online per-user erasure would require a broader barrier/lease design across all writers and in-flight commits. That redesign is outside this patch. Access blocking alone does not prevent an already running worker from committing.

`noeis-support-erasure-schema-inventory-2026-10-11.json` enumerates all 80 registered models from the current source: 77 directly scoped, two Board-dependent models, and one global OAuth control model. It contains schema metadata, not live counts.

| Library/Think/Wiki/Editions | Account `userId` records, embedded highlights/notes/PDF data, revisions/proposals, source events, maintenance runs, agent threads/actions, receipts, cached briefings and share snapshots. Children embedded in owned documents leave with their parents. |

| Shared/cross-account material | Remove owned share snapshots according to approved scope. Inspect references, contributions, display names and original-source metadata in other users' records; do not blindly delete their data. Public copies outside NOEIS cannot be recalled by this patch. |

## Backups, logs and truthful retention boundaries

Active database cleanup does not erase manual Mongo/Wiki archives, filesystem product-event logs, platform logs, analytics, provider request records or snapshots. Restore procedures must replay deletion handling before reopening ingress or workers; restoring a pre-erasure snapshot must not reactivate the account or replay its jobs. The operator must choose a minimal retained deletion record/restore exclusion method and its duration before use.

Known source behavior remains: no general content expiry; one-hour connector access tokens; 30-day refresh grants with asynchronous record cleanup one day after expiry; revoked/expired access records have no automatic purge rule. Successful manual archives and product-event files have no defined automatic expiry. Ephemeral Render filesystem loss is separate from platform log retention.

Actual Render workspace retention, Atlas backup configuration, OpenRouter privacy/logging/budget controls and Vercel analytics retention remain unverified. Do not substitute vendor defaults or historical cluster notes for this account's settings. Define and disclose any justified retained records, their purpose, access and timeline. Do not claim zero data retention or immediate backup erasure.

[OpenAI's Security & Privacy guide](https://developers.openai.com/plugins/guides/security-privacy) calls for a published retention policy and respect for deletion requests. No self-service deletion-button requirement was found in the reviewed text. A working support-led procedure can therefore be considered, but this local patch does not establish operating readiness or platform approval.

## Synthetic verification and limits

Tests use unusable synthetic credential values and a fresh temporary local MongoDB started from an already cached binary, with runtime download disabled. They exercise current-account checks, denied login/personal-agent/bridge/import access, OAuth closure after consent/refresh, scoped and retryable revocation, partial failure, legacy users without a marker, mixed string/ObjectId queue ownership, Board child scopes after parent removal, other-account preservation, and restart refusal with unresolved records/jobs/storage.

No test connects to the application database or calls a paid model/provider. No production end-to-end erasure or operating maintenance window has been verified. The operator must still reconcile the live inventory and prove process quiescence before application.

The added lookup is one indexed database read per valid credential boundary. A database outage denies access; this is an intentional availability tradeoff. Approval and regression verification on then-current main are required before merging/deploying this security behavior. No UI, account setting, legal publication, live grant or production retention rule is changed by this local work.
